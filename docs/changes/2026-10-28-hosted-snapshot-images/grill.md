# Hosted Snapshot 中的本地图片

## Confirmed details

以下对自由回答的理解和待验证事项经 Review 完成确认。

- **Q6，你的回答：** 快照超出大小限制时，发送者可选择自动压缩图片，或自行调整文件后重试。
- **待验证：** Hosted Snapshot 的大小上限将在核对上传服务、接收端能力和存储成本后确定。

## Question history

### Q1. 图片应该随哪种 Snapshot 分享？

> **Your decision: A.** 先支持 Hosted Snapshot。

目前 Link Snapshot 把内容放在链接里，Hosted Snapshot 把加密内容存到服务器；两者都不携带本地图片。你希望先在哪种分享方式中支持本地图片？

- **A. 先支持 Hosted Snapshot。** 分享时把本地图片与文档一起加密上传。图片不会撑长链接，但使用这项能力需要 Hosted Snapshot。
- **B. 两种 Snapshot 都支持。** Link Snapshot 也把图片放进链接。两种方式能力一致，但图片可能让链接过长而无法发送。
- **C. 暂时不打包图片。** 保持现有分享方式，只提醒图片不可用。改动最少，但接收者仍无法看到本地图片。

**Recommended: A.** 图片容易让链接变得很长，Hosted Snapshot 更适合承载图片；代价是需要上传加密数据。

### Q2. 这次最想解决谁的什么问题？

> **Your decision: A.** 让他人完整阅读文档。

这次讨论源于有人希望向非技术同事发送可读的 Markdown 链接，而本地图片不会随 Markside 的 Snapshot 显示。你最看重哪种使用场景？

- **A. 让他人完整阅读文档。** 发送者分享包含本地图片的文档，接收者在浏览器中阅读。目标清楚，但暂不以共同修改图片为目标。
- **B. 改善审阅和反馈。** 接收者看图后提出 Review Comments，再把 Review 发回作者。更关注反馈往返，可能需要检查现有 Review 体验。
- **C. 同时满足阅读和审阅。** 两种场景都是这次的目标。覆盖更广，但可能需要更多验证。

**Recommended: C.** Markside 已支持接收者阅读和回传 Review，图片应在这两个场景中都可见；验证范围会稍大。

### Q3. 有图片无法读取时，是否允许继续分享？

> **Your decision: A.** 提示后允许继续。

例如图片已经被移动，或 Markside 无法访问它。接收者打开快照时，这张图片无法显示。

- **A. 提示后允许继续。** 列出无法读取的图片，让发送者选择继续或取消。其他内容仍可分享，但接收者会看到缺图。
- **B. 阻止分享。** 所有本地图片都读取成功后才能创建 Hosted Snapshot。快照更完整，但一张缺图会阻止整份文档分享。

**Recommended: A.** 发送者可以判断缺图是否影响阅读，但需要主动留意提示。

### Q4. 是否自动打包引用的本地图片？

> **Your decision: A.** 自动打包，并在分享前说明。

选择 Hosted Snapshot 时，Markside 可以读取文档引用的图片，并与文档一起加密上传。拥有完整链接的人也能看到这些图片。

- **A. 自动打包，并在分享前说明。** Markside 收集引用的本地图片，在确认界面显示图片数量和上传提示。操作简单，但用户需要留意提示。
- **B. 让发送者每次选择是否打包。** 分享界面提供开关，发送者可选择只分享文字。控制更细，但增加一次选择，也可能因未开启而出现缺图。

**Recommended: A.** 完整阅读是这次的目标，明确说明图片也会上传即可；发送者仍可取消分享。

### Q5. 是否继续以原地址加载网络图片？

> **Your decision: A.** 网络图片保持原地址。

文档也可能引用 HTTPS 图片。这些图片由其他网站提供，接收者能否看到它们取决于该网站的访问权限和图片是否仍存在。

- **A. 保持原地址。** 只打包本地图片，网络图片仍由接收者的浏览器加载。改动范围较小，但网络图片可能失效或暴露接收者的访问。
- **B. 连同网络图片一起打包。** 分享时尝试获取并加密上传网络图片。快照更独立，但读取权限、隐私和失败处理会更复杂。

**Recommended: A.** 先解决本地图片缺失，保留网络图片现有行为；网络图片的可用性仍取决于原网站。

### Q6. 遇到图片导致快照超过大小限制时，怎么处理？

> **Your decision:** 超过限制时让用户选择自动压缩或者手动调整。

Hosted Snapshot 目前沿用 256 KiB 的解码内容上限，图片通常比文字大得多。支持图片需要调整上限，具体数值还要核对上传服务和接收端能力。

- **A. 说明超出限制，让发送者调整后重试。** Markside 显示大小和限制，发送者可以压缩或移除图片。快照内容完整且行为明确，但多一步手动处理。
- **B. 自动缩小图片后分享。** Markside 在需要时压缩或缩放图片。分享更省事，但图片质量可能下降，也需要明确处理透明和动态图等情况。
- **C. 跳过超限图片并允许继续。** Markside 告知哪些图片未打包，发送者可选择继续。操作灵活，但接收者可能看到缺图。

**Recommended: A.** 首版保留原图，避免未经确认改变图片质量；超过限制时需要发送者调整。

### Q7. 本地图片引用可以指向文档所在文件夹之外吗？

> **Your decision: A.** 打包所有能读取的本地图片。

Markside 当前预览可解析 `../assets/chart.png` 和 `file:///...` 这样的本地引用，图片可能位于文档目录之外。

- **A. 打包所有能读取的本地图片。** 相对路径、上级目录和绝对文件路径都按现有预览解析。更多现有文档可以完整分享，但用户需要留意分享前的图片清单。
- **B. 仅打包文档所在文件夹及其子文件夹中的图片。** 文件夹以外的图片视为无法打包。范围更容易理解，但一些已能预览的图片会在分享时缺失。

**Recommended: A.** 与现有预览的引用方式保持一致；分享前应说明哪些图片将被上传。

### Q8. 自动压缩会改变图片时，是否先让发送者确认？

> **Your decision: A.** 显示压缩结果并让发送者确认。

超出大小限制时，发送者可以选择自动压缩或自己调整文件。自动压缩可能缩小图片尺寸、降低画质，也可能无法保留动画或 SVG 的原有内容。

- **A. 说明结果并让发送者确认。** Markside 先尝试压缩，再显示压缩前后的大小和无法保留原样的图片；发送者确认后才上传。结果更透明，但分享多一步。
- **B. 选择压缩后直接上传。** Markside 尝试压缩并立即创建快照。步骤更少，但发送者可能不知道图片发生了什么变化。

**Recommended: A.** 图片可能因此改变，上传前让发送者检查结果更可靠；需要额外确认一次。

### Q9. 自动压缩无法保持动画或 SVG 时，怎么办？

> **Your decision: A.** 保留动画和 SVG 原图，仍超限时手动调整。

自动缩小或重新编码可能使 GIF 等动态图失去动画，也可能把 SVG 变成普通位图。发送者可以选择手动调整原文件。

- **A. 保留原图，并在仍超限时让用户手动调整。** 自动压缩只处理能够保留预期显示效果的图片。动画和矢量图不会被静默改变，但压缩可能不足。
- **B. 允许转换，并在确认时说明。** 必要时把动态图或 SVG 转成静态图片。更可能满足大小限制，但可能丢失动画或清晰度。

**Recommended: A.** 保持图片的主要表现，避免接收者看到与原文不同的内容；少数文档可能需要手动调整。

### Q10. 图片快照的大小上限如何确定？

> **Your decision: C.** 由技术验证决定上限。

当前接收端限制解码后的快照内容为 256 KiB。加入图片需要提高 Hosted Snapshot 的限制，并同时考虑上传服务、接收端内存和存储成本；现阶段还没有确认这些部分能支持的最大值。

- **A. 先以 10 MiB 为总大小目标，再验证可行性。** 文档和图片合计以 10 MiB 为设计目标，实施前核对服务和接收端限制。目标具体，但验证后可能需要调整。
- **B. 先以 5 MiB 为总大小目标，再验证可行性。** 文档和图片合计以 5 MiB 为设计目标，实施前核对限制。存储占用较低，但更多图片可能需要压缩。
- **C. 由技术验证决定上限。** 根据现有服务限制、成本和代表性文档选定具体数值，再向你报告。避免现在猜数字，但产品容量要等验证后才能确定。

**Recommended: C.** 现有服务的真实限制尚未核对，先验证可以避免承诺不可用的容量；具体数字需要随后确定。

### Q11. 哪些本地图片引用需要打包？

> **Your decision: A.** 支持 Markdown 图片和 HTML 的 img。

文档可以使用 Markdown 图片语法，也可以在原始 HTML 中使用 `<img>` 标签。两种写法都可能指向本地图片。

- **A. 支持 Markdown 图片和 HTML 的 img。** 两种写法中可读取的本地图片都被打包。更贴近现有预览，但处理范围较大。
- **B. 先只支持 Markdown 图片。** 只打包 Markdown 图片语法引用的本地图片。实现范围较小，但 HTML 图片仍可能缺失。

**Recommended: A.** 发送者关心的是分享后图片是否可见，两种已有写法都应覆盖；需要额外验证 HTML 中的图片。

### Q12. 有本地图片时，是否默认选择 Hosted Snapshot？

> **Your decision: A.** 有本地图片时默认选择 Hosted Snapshot。

现在 Markside 根据链接长度预选分享方式，发送者仍可自行选择。Link Snapshot 不会打包本地图片。

- **A. 有本地图片时默认选择 Hosted Snapshot。** 发送者仍可切换到 Link Snapshot，切换后会看到本地图片不可用的提示。默认分享更完整，但默认选项会上传加密内容。
- **B. 保持现有默认规则。** 继续根据链接长度选择分享方式，并提醒 Link Snapshot 不含本地图片。上传行为与现在一致，但发送者可能需要手动切换。

**Recommended: A.** 默认选项更符合完整阅读的目标，同时保留发送者的选择；确认界面需要说明上传。

### Q13. 自动压缩后仍超出上限时怎么办？

> **Your decision: A.** 自动压缩仍超限时说明并让发送者手动调整。

部分图片可能无法进一步压缩，或者文档中包含需要保留原样的动画和 SVG。

- **A. 说明仍超限，提供返回手动调整。** 不上传超限快照，发送者可以取消并调整原文件后重试。行为明确，但无法立即分享。
- **B. 允许选择排除部分图片后继续。** 发送者选择不打包哪些图片，再创建快照。可以尽快分享，但接收者看到的文档会不完整。

**Recommended: A.** 保持超限时需要调整的规则，避免额外的图片筛选流程；发送者需要手动处理文件。
