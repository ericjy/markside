# 网上 Markdown 预览

## Confirmed details

以下范围和待验证事项由用户在完成 Review 时确认。

- **之前的讨论：** 网上 Markdown 第一版只读，不接管 GitHub 和 GitLab 已经渲染好的仓库页面。
- **待验证：** 某些网站可能阻止图片或其他资源加载；直接下载的文件可能无法预览。Chrome 权限提示和更新时的表现也需要实测。

## Question history

### 之前讨论的摘要

用户希望避免寻找 Markdown 扩展来阅读网上 `.md` 的人因为 Markside 不支持而失望。用户同意支持所有网站上的原始 Markdown，以 GitHub Raw 和 GitLab Raw 为重点测试案例，第一版只读，暂不接管已经渲染好的 GitHub 或 GitLab 仓库页面。是否默认自动渲染，在讨论 Chrome 权限和竞品后尚未最终确定。

### Q1. 网上 Markdown 应该怎样开启自动渲染？

> **Your decision: A.** 用户选择开启所有网站的自动渲染。

Chrome 要让 Markside 自动识别任意网站的文件，需要用户允许它访问网站。这个权限的提示可能说 Markside 可以读取和更改网站数据，具体提示需要在 Chrome 中验证。

~~~mermaid
flowchart LR
  A[打开网上的原始 Markdown] --> B[Chrome 判断 Markside 是否有网站访问权限]
  B --> C[Markside 渲染文件]
~~~

- **A. 用户选择开启所有网站的自动渲染。** 初次使用时说明权限，由用户选择是否授权；授权后兼容的网上 Markdown 自动渲染。设置一次后体验简单，但用户会看到范围较大的权限提示。
- **B. 用户逐个授权网站。** 用户在需要时允许 Markside 访问当前网站，之后这个网站的文件自动渲染。权限范围较小，但每遇到一个新网站都需要操作。
- **C. 安装时要求所有网站权限。** 安装或更新时请求网站访问权限，接受后兼容的网上 Markdown 自动渲染。使用最直接，但权限提示可能影响安装，现有用户更新时也可能需要重新同意。
- **D. 每次手动渲染当前页面。** 用户打开文件后点击 Markside 来渲染。无需长期访问所有网站，但每次都多一步。

**Recommended: A.** 授权一次后能自动渲染不同网站的文件，也让现有用户自行决定是否开启；代价是开启时仍需接受较大的权限。

#### Compare tradeoffs

| 考虑 | A. 一次开启 | B. 逐站授权 | C. 安装时要求 | D. 每次点击 |
|---|---|---|---|---|
| 后续使用 | ✓ 自动渲染 | △ 新网站需授权 | ✓ 自动渲染 | ✕ 每次点击 |
| 网站访问范围 | △ 授权所有网站 | ✓ 用户选择的网站 | △ 所有网站 | ✓ 临时访问当前页面 |
| 现有用户更新 | ✓ 功能可选 | ✓ 功能可选 | △ 可能需要重新同意 | ✓ 无需广泛网站权限 |

### Q2. 用户在哪里开启网上文件的自动渲染？

> **Your decision: A.** 在扩展弹窗和设置中提供入口。

用户打开一个原始 Markdown 页面后，Markside 需要一个容易找到的入口来说明并请求网站权限。

- **A. 在扩展弹窗和设置中提供入口。** 用户打开网上文件时可从扩展弹窗开启，也可以随时在设置里开启。入口容易发现，但第一次仍需用户点击扩展。
- **B. 只在设置中提供入口。** 用户进入设置，找到在线预览并开启。界面更简单，但在文件页面上不容易发现。
- **C. 在首次安装时提示开启。** 安装后介绍在线预览，用户可以立即授权或跳过。新用户更容易发现，但会打断只想处理本地文件的人。

**Recommended: A.** 在用户正在打开文件时提供入口，同时保留设置入口；第一次仍需点击扩展。

### Q3. 用户关闭自动渲染时，网站权限应该怎样处理？

> **Your decision: A.** 关闭自动渲染时同时撤销相关网站权限。

开启自动渲染会请求网站访问权限；之后用户可能希望停止这个功能。

- **A. 关闭时同时撤销网站权限。** 用户在设置中关闭自动渲染后，Markside 也放弃为此取得的网站访问权限。权限与开关一致，但再次开启需要重新授权。
- **B. 关闭渲染，但保留网站权限。** 用户可以再次开启而不用重新授权。操作方便，但关闭功能后权限仍然存在。

**Recommended: A.** 关闭功能时同时撤销权限更容易理解，代价是重新开启时需要再次授权。

### Q4. 用户没有开启自动渲染时，还能预览当前文件吗？

> **Your decision: A.** 允许手动预览当前文件。

用户可能只想偶尔阅读网上的 Markdown，不想长期授权所有网站。

- **A. 允许手动预览当前文件。** 用户点击扩展弹窗中的预览操作，即可预览当前兼容文件。偶尔使用更方便，但每次都需要点击。
- **B. 必须先开启自动渲染。** 只有授权所有网站后才能预览网上文件。入口更简单，但偶尔使用的人也必须授权。

**Recommended: A.** 偶尔使用不必长期授权，代价是多一个入口。

### Q5. 网上文件中的相对图片和链接如何处理？

> **Your decision: A.** 相对图片和链接按原文件地址打开。

Markdown 可以引用同一网站上的图片和其他文档；这些地址通常相对于当前文件。

- **A. 按原文件地址打开。** 图片使用原地址显示，链接按原地址打开，Markdown 链接按用户的自动渲染设置处理。阅读方式自然，但网站限制可能使部分资源无法加载。
- **B. 不加载相对资源。** 图片和链接保留为文字或普通地址。行为简单，但很多网上文档会缺少内容或无法方便地导航。

**Recommended: A.** 保留网上文档正常的阅读和导航方式；个别网站的限制需要验证和提示。

### Q6. 页面不符合预览条件或渲染失败时怎么办？

> **Your decision: A.** 失败时保留原页面，主动预览失败时说明原因。

有些链接会下载文件，或者网站的设置不允许 Markside 正常显示内容。

- **A. 保留原页面并说明原因。** 自动渲染不成功时保留原页面；用户主动点预览失败时，在弹窗中给出说明。用户仍可访问原内容，但有些失败原因需要验证才能准确说明。
- **B. 显示错误页面。** 一旦识别到 Markdown 链接但预览失败，就用错误页面替代原内容。错误明显，但用户需要返回原页面才能继续。

**Recommended: A.** 不妨碍用户继续查看原内容，主动操作失败时也能得到反馈。

### Q7. 网上文件的预览提供哪些功能？

> **Your decision: A.** 提供目录、外观设置、复制渲染内容和 PDF Export。

网上文件第一版是只读的；本地文件的编辑、保存和 Review 依赖本地工作流程。

- **A. 提供阅读功能。** 保留目录、外观设置、复制渲染内容和 PDF Export。用户能舒适阅读和导出，但不能编辑或添加 Review Comment。
- **B. 只显示渲染后的正文。** 不提供目录、外观设置或导出。界面简单，但与本地阅读体验差距较大。

**Recommended: A.** 网上文件也应有完整的阅读体验，第一版保持只读。

### Q8. 用户怎样查看原始 Markdown？

> **Your decision: A.** 提供原文和预览的切换按钮。

自动渲染后，用户有时仍想看网站原本提供的纯文本。

- **A. 提供切换原文和预览的按钮。** 用户可以在当前页面切换，重新加载后按自动渲染设置显示。查看原文方便，但工具栏会多一个按钮。
- **B. 只能通过关闭自动渲染查看原文。** 用户先关闭设置再重新加载。界面少一个按钮，但临时查看原文较麻烦。

**Recommended: A.** 临时查看原文不应要求更改设置，代价是增加一个控件。

### Q9. 哪些网上文件名应尝试作为 Markdown 预览？

> **Your decision: A.** 支持 .md、.markdown 和 .mdx 等所列后缀。

有些网站使用不同的 Markdown 文件后缀，另一些链接没有后缀或会触发下载。

- **A. 支持常见 Markdown 后缀。** 先支持 .md、.markdown 和 .mdx，包括带查询参数的链接。覆盖常见地址，但没有后缀或直接下载的文件可能不适用。
- **B. 只支持 .md。** 先解决最常见的文件。范围小，但其他常见后缀不能预览。
- **C. 也尝试没有后缀的地址。** 除常见后缀外，根据网站提供的文件类型识别。覆盖更多文件，但识别和浏览器下载行为需要额外验证。

**Recommended: A.** 覆盖常见文件名，同时保持识别规则清楚；无后缀和下载型响应留待验证。

### Q10. 是否用这次决定更新原有的 Web Preview 提案？

> **Your decision: A.** 以这次决定更新提案。

现有提案设想每次手动触发，刷新后恢复原文，也没有原文切换功能。这次选择了开启后自动渲染、手动预览和原文切换。

- **A. 以这次决定更新提案。** 后续设计会按这次访谈修改旧提案，并验证 Chrome 权限和网站限制。方案符合刚才的选择，但需要重新核对旧提案细节。
- **B. 保留旧提案的方式。** 继续采用每次手动触发，刷新后恢复原文。沿用现有设计，但与刚才选择的自动渲染和原文切换不同。

**Recommended: A.** 让提案与刚才的决定一致，具体权限和兼容性仍需验证。
